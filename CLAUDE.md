# jjournal.nvim

## Ways of working

Work is planned and defined as user stories, tracked as individual markdown files that move through directories under `spec/`:

```
spec/backlog/   -- defined, not yet scheduled
spec/todo/      -- scheduled, not yet started
spec/doing/     -- actively being worked on
spec/done/      -- complete
```

A story moves through these stages by moving its file: `spec/backlog/story-name.md` -> `spec/todo/story-name.md` -> `spec/doing/story-name.md` -> `spec/done/story-name.md`. Only one story should normally be in `doing/` at a time.

Every change should be tied to a story that is in `spec/doing/` at the time the change is made. If a change is needed and no story covers it, stop: create the story first (see the template below), move it into `spec/doing/`, and only then make the change. This applies to process and tooling changes in this repo (CLAUDE.md, tests, CI config, etc.) just as much as to plugin features — small or "obvious" changes aren't exempt.

Adding new stories to `spec/backlog/` is exempt from this rule — planning isn't itself a change, so it can happen without a story of its own. This should usually happen when nothing is in `spec/doing/`. The exception: if the new stories are a direct byproduct of the story currently in `doing/` (an edge case being deferred, a bug spotted while implementing, a related future enhancement), they can be added to `spec/backlog/` while that story is still in progress.

If new work clearly reworks or extends a story already in `spec/done/`, don't edit the delivered content describing what was already built. Instead, move the file back into `spec/doing/` and append a new section describing the changed requirement, then proceed as normal. This keeps one file as the running history of a piece of functionality — original delivery plus later revisions — rather than silently rewriting delivered history or spawning a disconnected duplicate story.

Each story is one file, named descriptively in kebab-case (e.g. `configurable-journal-path-template.md`), and follows this template:

```markdown
## **Story: <short title>**

**Use Case:** <why this matters, from the user's perspective>

### **Acceptance Criteria**

* **Given** <context>,
* **When** <action>,
* **Then** <expected outcome>.

### **Busted Test Cases**

​```
it("<behavior being tested>", function()
    -- arrange / act / assert using the busted framework
end)
​```
```

Acceptance criteria are written as Given/When/Then. Test cases are written as busted specs (see `tests/`) that initially fail and pin down the acceptance criteria in code.

## Testing

We practice test-first development: for any story, write the failing busted test(s) before writing the implementation that makes them pass.

We aim for 100% test coverage. Check `luacov.report.out` (generated by `./tests/scripts/run.sh`) for uncovered lines and add specs to close any gaps. Line coverage alone isn't the goal, though: it won't catch an untested branch inside a single-line expression (e.g. a ternary), an untested default value, or a mapping that's registered but never verified to do the right thing when triggered. When adding specs, think about the full interface being exercised, not just which lines execute.

Specs in `tests/jjournal_spec.lua` are organized one `describe` block per public function (`jjournal.resolve_date`, `jjournal.open_date`, `jjournal.setup`, etc.), mirroring `lua/jjournal/init.lua`'s public interface. Avoid ad-hoc or overlapping groupings (e.g. a generic "actions" or "setup" bucket) — if two describe blocks end up covering the same function, merge them.

All mocking goes through `setup_test` in `tests/support/setup_test.lua`. Tests should never call `luassert.stub` directly — describe what to mock via the `mocks` table passed to `setup_test`, and pass the test body itself as the second argument, `test_fn`. `setup_test` installs the mocks, runs `test_fn`, and always cleans up afterward (reverting stubs and restoring `jjournal.config`) — even if `test_fn` errors (e.g. a failed assertion) — so cleanup can't be skipped or forgotten the way a separately-called `cleanup()` could be. This keeps mocking mechanics out of individual tests. `setup_test` supports mocks for `vim.fn`, `vim.api`, `vim.ui`, `vim.keymap`, the `vim` global itself, and the `jjournal` module, plus a `config` override for `base_dir`/`file_path`/`use_default_mappings` and an `on` escape hatch for stubbing arbitrary tables (e.g. a fake `telescope.builtin`). Mocks are installed before `setup_test`'s internal `jjournal.setup()` call, so it also captures setup's own side effects (keymap binding, autocmd registration) — most tests don't need to call `setup()` again themselves.

If most specs in one `describe` block repeat the same `mocks` shape, consider a small local helper scoped to that block that wraps `setup_test` with the shared defaults (via `vim.tbl_deep_extend("force", defaults, overrides or {})`), rather than repeating the same mocks table in every `it`. See `setup_open_date_test` in the `jjournal.open_date` describe block, or `setup_status_test` in the nested `journal buffer status autocmd` block, for examples. This still goes through `setup_test` — it's a convenience layer on top, not an alternative mocking mechanism.

The bar for adding one of these helpers isn't just "this reduces duplication" — it's whether it makes the test's intent and mechanism clearer by surfacing the one or two fields that actually vary and hiding the boilerplate that doesn't. Before adding one, check whether the repeated fields are a genuinely fixed default (good candidate) or whether they're actually the thing each test is varying, just with different values each time (not a good candidate — factoring it out would only move the override into every call site with no reduction in noise). For example, `jjournal.resolve_date`'s specs each pass a different `fn.readdir`/`fn.expand` — that's the test data itself, not a default, so a shared-defaults helper wouldn't help there. If a proposed helper would leave most calls fully overriding the "default" anyway, or would obscure which field a given test cares about, it's making things worse, not better — skip it.

Avoid undeclared globals in spec files. Busted normally injects `describe`/`it` as implicit globals via `setfenv`, but that only works because `.luarc.json` tells lua_ls to treat them as known globals — masking any *other* accidental undeclared global. Instead, require them explicitly at the top of the spec file: `local describe, it = require("busted").describe, require("busted").it` (this works because `require("busted")` returns the same already-initialized module the runner uses internally). `vim` is the only global we declare in `.luarc.json`, since it's a genuine Neovim runtime global with no require path.

Avoid busted's test lifecycle functions (`before_each`, `after_each`, `setup`, `teardown`). They spread state-setup logic across a file, away from the test that depends on it, and make a single test hard to read in isolation. Prefer passing the test body into a shared, reusable helper (like `setup_test`) that wraps setup and cleanup around it, rather than framework hooks.

## Before committing

Work through this checklist before committing. If a check surfaces a gap, stop, fix it, and wait for confirmation before committing — don't fold an unreviewed fix into the commit silently.

* **Tests pass.** Run `./tests/scripts/run.sh` and confirm all specs pass.
* **Interface fully exercised, not just lines executed.** Review the diff against the full interface being exercised (see "Testing" above): every new/changed branch, default value, and wiring point should have a spec pinning it down, not just enough to hit each line once. If something's missing, add the spec before committing.
* **Docs are current.** Check whether `README.md`, `doc/jjournal.txt`, and this file still accurately describe the change. Update whichever are now stale.
* **Backlog still makes sense.** Check whether this change makes any `spec/backlog`, `spec/todo`, or `spec/doing` story redundant, already done, or in need of rewording. Update or remove it.
* **Nothing stray is staged.** Check `git status`/`git diff --cached` for accidentally-included generated files (`doc/tags`, `luacov.*.out`, etc.) or unrelated changes.
* **Story location matches reality.** At most one story should be in `spec/doing/`, and it should move to `spec/done/` once the work is actually complete.
