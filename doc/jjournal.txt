1. Introduction                                      *jjournal-introduction*

jjournal.nvim is a minimal daily journaling plugin. Each day is a single
file named by date, nested under year/month directories by default (e.g.
`2026/07/2026-07-09.md`), or laid out however you like via
|jjournal-config-file_path|, inside a configured journal folder. It
provides mappings to jump to today's entry, step or skip to the
previous/next entry (see |jjournal-mappings| for the difference), jump to
an arbitrary date, and search across your journal backlog.

==============================================================================
2. Setup                                                    *jjournal-setup*

Call setup() once, typically from your plugin manager's config or
`init.lua`: >lua

    require("jjournal").setup({
      base_dir = "~/notes/journals/",
      file_path = "%Y/%m/%Y-%m-%d.md",
      use_default_mappings = true,
      search = "auto",
    })
<
All fields are optional; the values shown above are the defaults.

If you have existing entries in the old flat `"%Y-%m-%d.md"` layout (the
default before this version), either set `file_path = "%Y-%m-%d.md"`
explicitly to keep them where they are, or move your existing files to
match the new nested layout yourself (e.g. with `zmv` in zsh) before
upgrading.

==============================================================================
3. Configuration                                     *jjournal-configuration*

                                                    *jjournal-config-base_dir*
base_dir~
    Type: `string`
    Default: `"~/notes/journals/"`

    Root directory where journal entries are stored. A trailing slash is
    optional. Where each entry lives beneath this root is controlled by
    |jjournal-config-file_path|.

    Validated at `setup()`: raises an error immediately if `base_dir`
    already exists as a regular file rather than a directory. If it
    doesn't exist yet (the normal case for a new journal) but its nearest
    existing parent directory isn't writable, `setup()` still completes
    (mappings and autocmds bind as usual) but warns with `vim.notify` at
    `ERROR` level, since permission checks aren't reliable enough across
    every filesystem to justify disabling the plugin over a possible false
    positive.

                                                   *jjournal-config-file_path*
file_path~
    Type: `string`
    Default: `"%Y/%m/%Y-%m-%d.md"`

    Template for each entry's path, relative to `base_dir`, built from date
    placeholders:

        %Y      4-digit year, e.g. `2026`
        %m      2-digit month, e.g. `07`
        %d      2-digit day of month, e.g. `09`
        %D      shorthand for the full date, i.e. `%Y-%m-%d`

    `/` in the template creates nested directories (created automatically
    the first time an entry is written, not when it's opened -- so merely
    opening and discarding an unwritten entry never creates one). For
    example: >lua

        file_path = "%Y/%m/%Y-%m-%d.md"    -- nested by year/month
        file_path = "%Y/%m/%d/journal-%D.txt"  -- year/month/day dirs,
                                                -- descriptive filename
<
    Navigation ([jj, ]jj, [j, ]j, etc.) identifies each file's date by extracting a
    `YYYY-MM-DD` substring from its filename alone, so the filename portion
    of the template (the segment after the last `/`) must contain either
    `%D` or the literal sequence `%Y-%m-%d`, written in that order. Any
    prefix, suffix, or extension around it is fine (or none); `setup()`
    raises an error if this isn't satisfiable, e.g. `"%Y/%m/%d.md"` (day
    only, no full date in the filename) is invalid.

                                          *jjournal-config-use_default_mappings*
use_default_mappings~
    Type: `boolean`
    Default: `true`

    Whether to bind the default mappings listed in |jjournal-mappings|. Set
    to `false` to define your own mappings against
    `require("jjournal").execute()` (see |jjournal-api|) instead.

                                                      *jjournal-config-search*
search~
    Type: `"auto"|"telescope"|"builtin"|function(base_dir)`
    Default: `"auto"`

    Controls what the backlog search (|jjournal-search|) uses. See
    |jjournal-search| for the full behavior of each value.

4. Default mappings                                       *jjournal-mappings*

Bound in normal mode when `use_default_mappings = true` (the default):

    gj              Open today's journal entry.
    [jj             Step to the previous day's entry.
    ]jj             Step to the next day's entry.
    [j              Skip to the previous existing entry.
    ]j              Skip to the next existing entry.
    <leader>jj      Prompt for a date and open it.
    <leader>jp      Pin the current journal buffer. See below.
    <leader>fj      Search the journal backlog. See |jjournal-search|.

`[jj`/`]jj`/`[j`/`]j`/`<leader>jp` are only mapped inside buffers
jjournal manages (bound per buffer as it's opened, rather than globally
at |jjournal.setup()| like `gj`/`<leader>jj`/`<leader>fj`) -- pressing
one of them anywhere else does nothing. Stepping and skipping are
relative to wherever you currently are, and pinning only means
something for a buffer jjournal already manages, so none of them are
useful (or, for pinning, even meaningful) outside a journal buffer --
unlike `gj`/`<leader>jj`/`<leader>fj`, which are entry points meant to
work from anywhere.

Stepping ([jj/]jj) shifts the current date by exactly one day in that
direction and opens it, creating it if it doesn't exist yet -- useful
for moving through consecutive days, including blank ones.

Skipping ([j/]j) jumps to the nearest entry that already exists (on
disk or in an open buffer) in that direction, without stopping at blank
days in between. Both work the same regardless of where today falls.

All four accept a count prefix: `3]jj` steps forward 3 days instead of
1; `2]j` skips to the 2nd existing entry in that direction instead of
the nearest one. With no count, both default to 1, matching the
behavior above. A count on `gj`, `<leader>jj`, or `<leader>fj` has no
effect.

Any journal buffer you haven't edited is closed automatically the
moment you navigate away from it, whether or not the file already
existed on disk -- if it never existed, nothing is written; if it did,
the file itself is untouched, only the buffer goes away. Editing it at
any point (even if you save and then navigate away with no unsaved
changes left) keeps it open for good from then on -- editing is a
one-way signal, not a live check of whether the buffer currently has
unsaved changes.

To keep an unedited buffer open on purpose -- e.g. an old entry you
want to keep referring back to -- `<leader>jp` pins it. There's no
unpin: close the buffer yourself (|:bdelete| or |:bwipeout|) if you
change your mind. A buffer still visible in another window is never
closed regardless of pin state, so splitting to view two entries side
by side needs no special handling.

To disable a single mapping while keeping the rest, set it to `false` on
`require("jjournal").mappings` before calling `setup()`: >lua

    require("jjournal").mappings["gj"] = false
    require("jjournal").setup({ use_default_mappings = true })
<

5. Buffer status                                      *jjournal-buffer-status*

Every buffer jjournal manages is tagged with buffer-local variables, so
any statusline plugin can read them directly, without depending on
jjournal's Lua API at all:

    vim.b.jjournal_entry    (boolean) `true` if jjournal manages this
                            buffer.
    vim.b.jjournal_date     (string) the entry's `YYYY-MM-DD` date.
    vim.b.jjournal_pinned   (boolean) `true` if the buffer is protected
                            from auto-cleanup (see |jjournal-mappings|);
                            unset otherwise.

|jjournal.pin_buffer()| also fires a `User JjournalPinned` autocmd and
calls `:redrawstatus` immediately after setting `vim.b.jjournal_pinned`.
`:redrawstatus` is enough for a statusline that reads these variables
fresh on every redraw, but a framework that caches its own rendered
output and only recomputes on specific autocmd events needs
`User JjournalPinned` added to that event list to notice the change
immediately rather than on the next unrelated event.

No UI ships with jjournal itself -- wire these into whatever statusline
you already use. See the README for an example using AstroNvim's
Heirline-based statusline (`astroui.status`).

6. Search providers                                          *jjournal-search*

`<leader>fj` (and `require("jjournal").execute("search")`) search the
journal backlog. The `search` config option (|jjournal-config-search|)
selects how:

`"auto"` (default)
    Uses telescope.nvim's `live_grep` if it's installed. Otherwise, falls
    back to the builtin search below with no warning.

`"telescope"`
    Always uses telescope. Warns and falls back to the builtin search if
    telescope isn't installed.

`"builtin"`
    Always uses Neovim's builtin |:vimgrep|: prompts for a search term,
    greps the configured journal base_dir recursively for files matching
    the extension configured via |jjournal-config-file_path| (`*.md` by
    default), and opens the results with |:copen|.

a Lua function
    Called directly as `function(base_dir)`, where `base_dir` is the
    configured journal root. Use this to wire up any other picker
    (fzf-lua, mini.pick, snacks.picker, etc.): >lua

        require("jjournal").setup({
          search = function(base_dir)
            require("fzf-lua").live_grep({ cwd = base_dir })
          end,
        })
<

7. Lua API                                                      *jjournal-api*

                                                            *jjournal.setup()*
setup({opts})
    Merges {opts} into the current config and (re-)binds mappings and
    autocmds. See |jjournal-configuration| for available keys.

                                                          *jjournal.execute()*
execute({target}, {cmd}, {count})
    Runs one of the mapping actions directly: {target} is one of "today",
    "step_prev", "step_next", "skip_prev", "skip_next", "prompt", "pin", or
    "search"; {cmd} is the Ex command used to open the result (e.g. "edit"
    or "vsplit"), ignored for "pin"/"search". {count} (default 1) is
    forwarded to |jjournal.resolve_date()|, ignored for "pin"/"search".

                                                     *jjournal.resolve_date()*
resolve_date({target}, {callback}, {count})
    Resolves {target} ("today", "step_prev", "step_next", "skip_prev",
    "skip_next", or "prompt") to a `YYYY-MM-DD` string (or `nil`), passed
    to {callback}. For "step_prev"/"step_next", {count} (default 1) is
    the number of days to shift; for "skip_prev"/"skip_next", it's which
    existing entry to jump to (1 = nearest). Ignored for "today" and
    "prompt".

                                                       *jjournal.open_date()*
open_date({date_str}, {cmd})
    Opens the journal entry for {date_str} with the Ex command {cmd}
    (default `"edit"`). Warns and does nothing if {date_str} is `nil`.

                                                     *jjournal.resolve_path()*
resolve_path({date_str})
    Resolves {date_str} (a `YYYY-MM-DD` string) to its full file path, per
    |jjournal-config-base_dir| and |jjournal-config-file_path|.

                                                   *jjournal.search_backlog()*
search_backlog()
    Runs the configured search provider. See |jjournal-search|.

                                                       *jjournal.pin_buffer()*
pin_buffer()
    Marks the current buffer as pinned, exempting it from the
    auto-cleanup described in |jjournal-mappings| regardless of whether
    it's ever edited. One-way: there's no unpin. Fires a `User
    JjournalPinned` autocmd and redraws the statusline -- see
    |jjournal-buffer-status|.
